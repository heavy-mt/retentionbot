# Retentionbot

Бот автоудаления новых сообщений Matrix для Element X. Работает поверх **включённого штатного
retention Synapse**, управляет политикой комнаты по JSON-командам администратора и отправляет
клиентам события удаления до серверного purge. Локальные вложения удаляет через Admin API.

Версия 0.1.0 — стенд и пилот. Поведение Element X на физических Android/iOS проверяется отдельно.
[Черновик ТЗ](docs/specification.md) · [Приёмка](docs/acceptance.md) · [Выбор БД](docs/database-choice.md).

## Сроки и штатный retention

Источник политики — `m.room.retention` комнаты и реальная конфигурация Synapse:
`default_policy`, `allowed_lifetime_min`, `allowed_lifetime_max`. Бот не отключает retention
и не заменяет серверные purge jobs. Команда меняет обычное состояние комнаты через Matrix API.

`max_lifetime` ограничивает срок серверного хранения. `min_lifetime` задаёт нижнюю границу
для действий бота. Synapse сам пока только сохраняет `min_lifetime`, не обеспечивая этот минимум
своей очисткой. Серверные `allowed_lifetime_min/max` ограничивают допустимый `max_lifetime`.
Бот приводит задаваемый максимум к этим границам и проверяет совместимость минимума.

Удаление планируется ближе к максимуму: по умолчанию за **пять минут до `max_lifetime`**, но не
раньше `min_lifetime`. Для редакций/реакций учитывается срок исходного сообщения и минимум
с момента отправки самой редакции/реакции. Если min равен max, запаса перед purge нет:
политика требует корректировки; бот показывает ошибку. Запас — `REDACTION_LEAD_SECONDS`.

Это не гарантия доставки до purge при любой аварии или нагрузке. Когда исходное событие уже
физически удалено, Synapse может принять redaction, но не выдавать её клиентам. Поэтому worker
дополнительно проверяет доступность созданного события удаления через клиентский API.
Ошибка `REDACTION_NOT_VISIBLE` сохраняется и не выдаётся за успешное уведомление клиента.

Уже удалённые данные не восстанавливаются. Команда `off` разрешена только когда у сервера нет
`default_policy.max_lifetime`; пустая политика комнаты иначе возвращает серверный срок.

## JSON-команды и ответы

Отправить обычное текстовое сообщение в комнату; допускается JSON в одну или несколько строк:

```json
{"command":"retention","action":"set","min_lifetime":"1h","max_lifetime":"7d"}
```

```json
{"command":"retention","action":"status"}
```

```json
{"command":"retention","action":"help"}
```

```json
{"command":"retention","action":"off"}
```

Сроки задаются строками `1h`, `1d`, `7d`, `30d`, другими целыми длительностями `s/m/h/d/w/y`
либо целым числом миллисекунд. Проверяются актуальное участие и power level автора команды
(по умолчанию от 100). Обычный участник может запросить help/status, но не изменить политику.
Ответ — JSON с понятным сообщением, результатом и значениями политики в миллисекундах.
Задержанное расшифрование старой команды не отменяет более позднюю настройку.

Бот учитывает сообщения **после успешного подключения к комнате**. При неудачной первой
попытке отсчёт начинается с последующего успешного вступления. Старую историю бот не redacts.
При этом изменение штатной политики влияет на всю историю, которую очищает сам Synapse.

## Compose и база данных

| Служба | Назначение |
| --- | --- |
| `observer` | Подключение комнат, E2EE, JSON-команды, синхронизация и планировщик |
| `worker` | Выполнение redaction, проверка её доступности, очистка медиа |
| `admin-gateway` | Ограниченные Admin API операции и чтение серверной конфигурации retention |
| `rabbitmq` | Доставка готовых задач удаления |
| `postgres` | Политики, метаданные событий, ссылки на файлы и состояние заданий |

Для указанной нагрузки **более 100 сообщений/с** в основной Compose включён
`postgres:18.6-bookworm`. Это отдельная БД бота; прямой записи в БД Synapse нет. Пользователь
приложения не superuser. Схемы бота и шлюза разделены. Данные PostgreSQL 18 сохраняются в томе
`postgres-data`, смонтированном в `/var/lib/postgresql`.

SQLite также поддерживается: без `DATABASE_URL` метаданные находятся в `/data/retention.db`,
для шлюза — `/data/gateway.db`. В Docker нужен постоянный локальный том `/data`, общий для
observer и worker. WAL работает на одном хосте; сетевые файловые системы для него не подходят.
Для основной поставки при выбранной нагрузке используется PostgreSQL. Криптохранилище SDK
остаётся локальным в `bot-data` независимо от движка метаданных.

Один observer. Worker можно масштабировать: `docker compose up -d --scale worker=4`.
Количество определяется по замерам Synapse и очереди. Выбор PostgreSQL сам по себе не доказывает
сквозную производительность 100+ сообщений/с: важны API лимиты, E2EE, задержки и диски.

RabbitMQ разворачивается этим же Compose. Его сеть `broker` — внутренняя; к ней подключены
только observer, worker и сам брокер. У gateway и PostgreSQL нет подключения к этой сети.
Нет опубликованных портов AMQP или management. Используются отдельные пользователь и vhost
`retention`. PostgreSQL тоже не публикует порт наружу.

## Подготовка Synapse

Нужен управляемый Synapse, локальный пользователь бота и административный токен для шлюза.
В федеративных комнатах возможность подключить бота зависит от прав локальных участников.
В пространства бот не вступает; обычные дочерние комнаты обслуживаются независимо.

1. Создать обычного пользователя, например `@retention:matrix.example.org`.
2. Подготовить административный токен Synapse.
3. Найти файл, содержащий итоговую конфигурацию retention, **который действительно загружается
   Synapse**. Рекомендуется отдельный retention-фрагмент без прочих секретов.
4. Убедиться, что `retention.enabled: true`. Существующие настройки сохраняются; пример
   [deploy/synapse-retention.yaml.example](deploy/synapse-retention.yaml.example) — ориентир,
   а не команда заменить текущую конфигурацию.

Тот же файл монтируется read-only в gateway. Путь задаётся `SYNAPSE_RETENTION_CONFIG_PATH`.
Файл должен быть доступен на чтение UID 10001; отдельную копию с независимыми настройками
использовать нельзя. Если retention распределён по нескольким файлам, выделить его итоговые
настройки в один действительно загружаемый фрагмент. После изменений перезапустить Synapse
и службы бота согласованно: изменение файла не означает, что работающий Synapse уже перечитал его.

Опциональное `redaction_retention_period: 0` ускоряет очистку исходного содержимого redacted-событий
фоновым заданием Synapse. Служебные оболочки событий и redaction могут оставаться до обычного purge.
Действующий `redaction_allowed_period` тоже должен позволять боту выполнять удаления.

Gateway приглашает бота через `make_room_admin`. После вступления бот снижает свои временные
права до необходимых для сообщений, redaction и `m.room.retention`, обычно 50. Ошибки комнат
видны в статусе; неполный охват приостанавливает физическую очистку файлов.

## Запуск

```bash
git clone https://github.com/heavy-mt/retentionbot.git
cd retentionbot
cp .env.example .env
mkdir -p secrets
chmod 700 secrets
openssl rand -hex 32 > secrets/gateway_secret
openssl rand -hex 32 > secrets/crypto_store_key
openssl rand -hex 32 > secrets/postgres_admin_password
chmod 600 .env secrets/*
```

Задать в `.env` адрес Synapse, `server_name`, ID бота, путь к настоящему retention-файлу и
**разные случайные hex-пароли** RabbitMQ/PostgreSQL. Для каждого подходит `openssl rand -hex 32`.
Сохранить административный токен в `secrets/synapse_admin_token`. Собрать образ и войти ботом:

```bash
docker compose build
docker run --rm -it --user "$(id -u):$(id -g)" \
  -v "$PWD/secrets:/out" retentionbot:0.1.0 login \
  --homeserver https://matrix.example.org \
  --user @retention:matrix.example.org --output /out
```

Пароль вводится интерактивно. Создаются настоящие устройство E2EE, `bot_access_token` и
`bot_device_id`. Токен не выводится. Для контейнеров на Linux:

```bash
sudo chown 10001:10001 secrets/*
sudo chmod 400 secrets/*
docker compose up -d --scale worker=4
docker compose logs -f observer worker admin-gateway
docker compose exec observer retentionbot status
```

`127.0.0.1` внутри контейнера означает сам контейнер. Synapse должен быть доступен по адресу
сервиса в общей сети либо по доступному адресу хоста. Брокер остаётся в отдельной внутренней сети.

## Логи и восстановление

Каждая запись — **один JSON-объект на одной физической строке**, без pretty print. Переносы
внутри сообщений экранируются. Например:

```json
{"timestamp":"2026-10-01T14:00:00+00:00","level":"INFO","component":"retentionbot.worker","message":"Содержимое сообщения удалено","event":"message.redacted","room_id":"!room:example.org","event_id":"$event"}
```

Тексты пользовательских сообщений, файловые ключи и токены не включаются в прикладные логи.
`status` тоже выдаёт JSON в одну строку. `docker compose logs` добавляет свой префикс; для получения
исходных строк использовать `docker compose logs --no-log-prefix observer worker admin-gateway`.

RabbitMQ получает только тип задачи и ID события/MXC. Очереди quorum/durable, сообщения persistent,
publisher confirms и manual ack. Дедлайны остаются в БД: TTL брокера не используется. Worker
повторно читает политику комнаты перед удалением. Повторные доставки используют стабильный Matrix
transaction ID. При потере задания планировщик восстанавливает его через пятиминутную аренду.

Ошибки API повторяются с задержкой; некорректные задания попадают в `retention.dead`.
После потери соединения PostgreSQL worker перезапускается с повторной доставкой незавершённого задания.
Планировщик делает индексные выборки просроченных событий по комнатам вместо полного просмотра
всей истории на каждом тике. Healthcheck проверяет свежесть синхронизации, не считает всю историю.

## E2EE и вложения

Бот — участник зашифрованных комнат. Его доступ к содержимому нужен для команд и поиска MXC.
Тексты и файловые ключи в БД заданий не сохраняются. При отсутствии ключа сохраняется ciphertext,
ключ запрашивается у отправителя. Истечение срока всё равно может вызвать redaction по ID;
физическая очистка ожидает расшифрования, чтобы не потерять ещё неучтённую ссылку.

`DEVICE_TRUST=tofu` запоминает первый ключ устройства для зашифрованных ответов и не доверяет
заменённому ключу того же устройства. Режим `verified` предназначен для подготовленного
криптохранилища; UI SAS/cross-signing в версии 0.1 нет. Перед пилотом проверить передачу ключей
от реальных Element X, особенно при запрете общения с непроверенными устройствами.

Локальный файл и миниатюры удаляются через Admin API после удаления последней учтённой ссылки
и паузы `MEDIA_GRACE_SECONDS` (60 секунд). Общий файл сохраняется, пока есть активная ссылка,
включая комнату без срока. Аватары, защищённые и загруженные до первого запуска gateway файлы
сохраняются: старые загрузки могут использоваться историей, которую бот не учитывает.

При неполном охвате, неизвестных ключах или непоправимом пропуске истории очистка файлов
приостанавливается. При пропуске после серверного purge бот продолжает получать новые события
и выполнять известные задания; потерянные ID восстановить обычным API нельзя. Ошибка комнаты
сохраняется в статусе. Пауза перед очисткой уменьшает риск общей ещё неучтённой ссылки, но API
не обеспечивает атомарности между новым сообщением и удалением файла.

Удаление на чужих серверах и во внешнем media repository требует отдельной интеграции.
Копии на телефонах, цитаты, медиакэш и резервные копии этой службой физически не стираются.
Element X может показывать отметку об удалении. Долгий офлайн клиента, особенно дольше срока
хранения самой redaction, требует отдельной приёмки; гарантии очистки любого локального кэша нет.

## Данные и проверки

Резервировать PostgreSQL, `bot-data`, `rabbitmq-data` и секреты согласованно. Потеря
криптохранилища может лишить бота ключей; потеря схемы gateway меняет границу старых загрузок.
Завершённые метаданные пока сохраняются. На большом потоке нужна отдельная политика архивации
и план диска: это открытый эксплуатационный пункт пилота.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/ruff check src tests
.venv/bin/pytest -q
```

Без внешних служб тесты используют SQLite. Для настоящего Synapse:

```bash
python3.12 -m venv .synapse-env
.synapse-env/bin/pip install matrix-synapse==1.161.0
SYNAPSE_PYTHON="$PWD/.synapse-env/bin/python" .venv/bin/pytest -q
```

`TEST_DATABASE_URL` включает повторение набора тестов на настоящем PostgreSQL в отдельных
тестовых схемах. `RABBITMQ_TEST_URL` включает реальную проверку повторной доставки; нужны
отдельные тестовые БД и broker/vhost. CI использует PostgreSQL 18.6 и RabbitMQ 4.3.6, собирает
Docker-образ и запускает Compose-проверку БД, брокера, worker, gateway и изоляции сети.

Первичные источники: [Synapse retention](https://element-hq.github.io/synapse/latest/message_retention_policies.html),
[Matrix redactions](https://spec.matrix.org/v1.16/client-server-api/#redactions),
[Synapse media API](https://element-hq.github.io/synapse/latest/admin_api/media_admin_api.html),
[официальные Docker-теги PostgreSQL](https://github.com/docker-library/official-images/blob/master/library/postgres).
