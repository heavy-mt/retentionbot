# Retentionbot

Служба автоудаления новых сообщений Matrix для Element X. Администратор комнаты задаёт срок
командой в чате. Служба отправляет стандартные события удаления, а локальные вложения удаляет
через API Synapse.

Версия 0.1.0 предназначена для стенда и пилотного внедрения. Проверена серверная логика и E2EE;
приёмка на физических телефонах Element X выполняется отдельно по [сценариям проверки](docs/acceptance.md).
Рамки для согласования с заказчиком: [черновик ТЗ](docs/specification.md).

## Возможности

- Подключение к существующим и новым обычным комнатам, включая приватные и личные переписки.
- Сроки `1h`, `1d`, `7d`, `30d` и отключение; отдельная настройка каждой комнаты.
- Изменение срока участниками с power level от 100; актуальные права проверяются на сервере.
- Обработка текста, вложений, редакций и реакций, включая зашифрованные сообщения.
- Сохранение очереди и контрольной точки синхронизации при перезапуске.
- RabbitMQ: постоянные задачи, publisher confirms, ручное подтверждение и повторная доставка.
- Повторная проверка срока перед удалением; изменение политики отменяет устаревшие задачи.
- Учёт ссылок на один файл из разных сообщений и комнат.
- Отдельный шлюз Admin API: административного токена нет у бота и обработчика задач.

Обработка начинается **после подключения бота к комнате**. История до этой точки сохраняется.
В пространства бот не вступает: пространство является каталогом комнат. Его обычные дочерние
комнаты обслуживаются независимо.

## Команды

| Команда | Действие |
| --- | --- |
| `!retention help` | Справка |
| `!retention status` | Срок, очередь, отсутствующие ключи и ошибки комнаты |
| `!retention set 1h` | Удаление через час |
| `!retention set 1d` | Удаление через сутки |
| `!retention set 7d` | Удаление через семь суток |
| `!retention set 30d` | Удаление через тридцать суток |
| `!retention off` | Отключение |

Смена срока распространяется на все учтённые сообщения комнаты. Редакции и реакции удаляются
по сроку исходного сообщения, если оно также учтено. Увеличение срока сохраняет ещё существующие
сообщения; уже выполненные удаления необратимы. Команды с задержанным расшифрованием не должны
отменять более позднюю настройку администратора.

## Состав

| Служба | Назначение |
| --- | --- |
| `observer` | Подключение комнат, E2EE, команды, получение событий, планирование задач |
| `worker` | Выполнение redaction и очистки медиа |
| `admin-gateway` | Ограниченные операции через Admin API Synapse |
| `rabbitmq` | Доставка готовых задач удаления |

SQLite хранит сроки, метаданные событий, ссылки на медиа и состояние выполнения. RabbitMQ
получает только тип задачи и ID события либо MXC файла. Сроки не реализованы через TTL RabbitMQ:
это позволяет менять политику комнаты после постановки задачи.

Поставка рассчитана на один сервер Linux, один observer и один worker. SQLite и криптохранилище
находятся в постоянном томе. Для нескольких серверов потребуется отдельная БД и координация
обработчиков. Единственный узел RabbitMQ сохраняет задачи при рестарте, но не обеспечивает HA.

## Подготовка Synapse

Нужен управляемый Synapse с локальной служебной учётной записью и административным токеном.
Токены передаются через файлы Docker secrets. Изменения делаются сначала на стенде.

1. Создать обычного пользователя бота, например `@retention:matrix.example.org`.
2. Подготовить административный токен Synapse для `admin-gateway`.
3. Применить настройки из [deploy/synapse-retention.yaml.example](deploy/synapse-retention.yaml.example)
   к существующей конфигурации и перезапустить Synapse.

В этой версии сроком исчезновения управляет Retentionbot. Штатный `retention.enabled` Synapse
нужно отключить, чтобы purge не удалял события раньше получения ботом. Настройка
`redaction_retention_period: 0` позволяет Synapse очищать исходное содержимое redacted-событий
на очередном проходе фоновой задачи (обычно до пяти минут). Служебная оболочка события и события
redaction сохраняются для протокола и синхронизации. Прямой записи в БД Synapse нет.

Отключение штатного retention влияет на весь homeserver. До запуска необходимо проверить
охват комнат: ошибки подключения показываются в `retentionbot status`. Все необслуживаемые
комнаты требуют отдельного решения; простое отключение retention без работающего бота не
обеспечивает автоудаление. Существующие политики `m.room.retention` этой версией не импортируются:
новые комнаты получают `DEFAULT_RETENTION`, затем управляются командами боту.

Для подключения шлюз использует `make_room_admin`: Synapse приглашает бота и временно выдаёт
максимальные доступные локальному участнику права. Бот вступает и снижает свой уровень до
необходимого для сообщений и redaction, обычно 50. Если локальные участники не могут выдать
нужные права, комната показывается с ошибкой подключения. В федеративной комнате нельзя
гарантировать административное подключение без прав её участников.

## Запуск через Docker Compose

```bash
git clone https://github.com/heavy-mt/retentionbot.git
cd retentionbot
cp .env.example .env
mkdir -p secrets
chmod 700 secrets
openssl rand -hex 32 > secrets/gateway_secret
openssl rand -hex 32 > secrets/crypto_store_key
chmod 600 .env secrets/*
```

В `.env` задать адрес Synapse, `server_name`, Matrix ID бота и случайный hex-пароль RabbitMQ.
Для пароля подходит результат `openssl rand -hex 32`. После настройки Synapse установить
`NATIVE_RETENTION_DISABLED=true`: observer требует это явное подтверждение конфигурации.

Сохранить административный токен в `secrets/synapse_admin_token` без кавычек. Затем собрать
образ и выполнить обычный вход бота, чтобы получить настоящее устройство для E2EE:

```bash
docker compose build
docker run --rm -it --user "$(id -u):$(id -g)" \
  -v "$PWD/secrets:/out" retentionbot:0.1.0 login \
  --homeserver https://matrix.example.org \
  --user @retention:matrix.example.org --output /out
```

Пароль вводится интерактивно. Команда создаёт `bot_access_token` и `bot_device_id`, не выводя
токен в терминал. Для контейнеров, работающих от UID 10001, на Linux настроить владельца файлов:

```bash
sudo chown 10001:10001 secrets/*
sudo chmod 400 secrets/*
docker compose up -d
docker compose logs -f observer worker admin-gateway
docker compose exec observer retentionbot status
```

Порты шлюза и RabbitMQ наружу не публикуются. Synapse должен быть доступен контейнерам по
`MATRIX_HOMESERVER`. Если он на том же хосте, `127.0.0.1` внутри контейнера означает сам контейнер:
используйте адрес сервиса в общей Docker-сети или доступный адрес хоста.

## Шифрование

Бот является участником зашифрованных комнат и получает ключи новых сообщений. Его доступ
к расшифрованному содержимому нужен для команд и поиска MXC вложений. Тексты и ключи файлов
в БД очереди не записываются. Пока ключ события отсутствует, сохраняется его ciphertext и
запрашивается ключ; удаление этого события ожидает расшифрования. Очистка медиа приостанавливается,
чтобы не удалить файл с ещё неучтённой ссылкой.

`DEVICE_TRUST=tofu` запоминает первый ключ устройства для отправки зашифрованных ответов.
Изменение ключа того же устройства вызывает отказ в доверии. TOFU не является ручной
верификацией личности. В режиме `verified` ответы ожидают верифицированные устройства.
Полного пользовательского интерфейса SAS/cross-signing в версии 0.1 нет; режим `verified`
предназначен для заранее подготовленного криптохранилища. Для пилота используется `tofu`.
Если Element X ограничивает передачу ключей непроверенным участникам, это необходимо проверить
на устройствах до включения политики в рабочей комнате.

## Физическое удаление вложений

- Удаляется локальный файл Synapse и связанные серверные миниатюры через Admin API.
- Очистка запускается после удаления последней учтённой ссылки и дополнительной паузы
  `MEDIA_GRACE_SECONDS` (по умолчанию 60 секунд).
- Файл сохраняется, пока на него ссылается хотя бы одно существующее учтённое сообщение,
  в том числе из комнаты с отключённым автоудалением.
- Аватары из полученных событий состояния и защищённые медиа сохраняются.
- Файлы, загруженные до первого запуска шлюза, сохраняются: они могут использоваться старой
  историей, которую бот не обрабатывает. Причина фиксируется в состоянии медиа.
- При неполном охвате комнат, пропуске синхронизации или отсутствии ключей очистка ожидает
  восстановления. Пауза уменьшает вероятность удаления ещё неучтённой общей ссылки; полной
  атомарности между новым сообщением и удалением файла API Synapse не предоставляет.
- Удаление файлов на чужих серверах и во внешнем media repository требует отдельной интеграции.
  В этой версии удаляются только локальные загрузки управляемого Synapse.

Скачанные на телефон копии, медиакэш приложения, цитаты в других сообщениях и резервные копии
живут по своим правилам. Удаление в интерфейсе Element X выполняется штатным способом: может
оставаться отметка об удалении. Служба не изменяет код клиента.

## Эксплуатация

Планировщик проверяет сроки каждые `POLL_SECONDS` (по умолчанию 5 секунд). Фактическая задержка
зависит от нагрузки, доступности Synapse/RabbitMQ, ключей и синхронизации приложения. Точные
пределы задержки устанавливаются по пилотным замерам.

Задачи защищены от повторной обработки: стабильный transaction ID Matrix и проверка БД перед
действием. При потере задачи после сбоя планировщик восстанавливает её через пятиминутную
аренду. Ожидаемые ошибки API сохраняются в БД и повторяются с задержкой. Некорректные задачи
попадают в очередь `retention.dead`; её наличие требует внимания администратора.

Резервировать согласованно тома `bot-data`, `gateway-data`, `rabbitmq-data` и секреты. Потеря
криптохранилища при сохранении ID устройства может лишить бота старых ключей. Потеря
`gateway-data` изменит границу сохранения старых файлов. БД очереди хранит метаданные завершённых
событий для идемпотентности; автоматическая архивация этих записей пока не реализована.

## Разработка и проверки

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e '.[dev]'
.venv/bin/ruff check src tests
.venv/bin/pytest -q
```

Интеграционные тесты сами запускают изолированный Synapse:

```bash
python3.12 -m venv .synapse-env
.synapse-env/bin/pip install matrix-synapse==1.161.0
SYNAPSE_PYTHON="$PWD/.synapse-env/bin/python" .venv/bin/pytest -q
```

Для проверки RabbitMQ указать `RABBITMQ_TEST_URL` тестового брокера. Используйте отдельный
брокер/virtual host: тесты работают с очередями `retention.jobs` и `retention.dead`.

Полезные первоисточники: [Matrix redactions](https://spec.matrix.org/v1.16/client-server-api/#redactions),
[Synapse retention](https://element-hq.github.io/synapse/latest/message_retention_policies.html),
[Synapse media API](https://element-hq.github.io/synapse/latest/admin_api/media_admin_api.html),
[RabbitMQ подтверждения](https://www.rabbitmq.com/docs/confirms).
