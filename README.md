# Retentionbot — серверная версия

Служба автоудаления новых сообщений Matrix для Element X. Создаёт события
`m.room.redaction` на стороне Synapse, которые клиенты получают через синхронизацию.
Штатный retention Synapse продолжает очищать серверную историю.

**Версия 0.2.0 работает без учётной записи бота и без изменения состава комнат.**
Поддерживаются обычные комнаты и Direct Messages, включая E2EE. Серверная служба
использует ID, автора, тип и время события. Расшифрование сообщений ей не требуется.

Статус: стенд и пилот. Интеграция закреплена за **Synapse 1.161.0**:
используются внутренние интерфейсы этой версии. Проверки на физических Element X
Android/iOS, целевая нагрузка и федеративный стенд входят в приёмку.

[ТЗ](docs/specification.md) · [Приёмка](docs/acceptance.md) · [Выбор БД](docs/database-choice.md).

## Компоненты

| Компонент | Работа |
| --- | --- |
| Модуль Synapse | Поток метаданных, фактическая политика retention, точечная redaction, JSON API управления |
| `observer` | Учёт новых событий, постоянная позиция потока, планирование сроков |
| `worker` | Задания удаления через модуль Synapse, повторы, сохранение результата |
| RabbitMQ | Постоянная очередь готовых заданий |
| PostgreSQL | Метаданные, сроки, состояние очереди и результаты |

Модуль читает события через хранилище Synapse и ограниченные SELECT-запросы.
События удаления и изменения политики создаются штатными обработчиками Synapse.
Служба не изменяет таблицы сообщений прямыми SQL-запросами.

Сообщение локального пользователя удаляется от имени его автора. Используется
административный механизм Synapse, позволяющий работать и после выхода автора
из комнаты. Если права комнаты запрещают автору redaction, используется подходящий
**существующий** локальный модератор. Для сообщений пользователей чужих серверов
нужен существующий локальный участник с правами удаления; при его отсутствии
задание откладывается с кодом `NO_LOCAL_MODERATOR`. Чужая учётная запись не подменяется.

## Retention и сроки

Источник настроек — конфигурация **работающего** Synapse и `m.room.retention`.
Копию `homeserver.yaml` служба не использует. `retention.enabled: true` обязателен.

Учитываются `default_policy`, `allowed_lifetime_min/max` и `min/max_lifetime` комнаты.
Synapse пока регистрирует `min_lifetime`, а служба проверяет нижнюю границу самостоятельно.
Серверные allowed-границы ограничивают максимальный срок.

По умолчанию redaction отправляется за **пять минут до max**, с соблюдением min.
Запас задаётся в конфигурации модуля: `redaction_lead: 5m`.
Если min равен max, положительного запаса нет: настройка отклоняется.
Для видимых серверу редакций и реакций учитываются время оригинала и минимум
с момента отправки самой редакции/реакции.

Это запас времени, а не согласованная блокировка всех purge jobs. При остановке службы,
перегрузке или коротких сроках сервер может успеть выполнить purge раньше redaction.
Уже исчезнувшее событие получает `missed / EVENT_PURGED`, а не успешный результат.
Сам сервер повторно проверяет актуальный срок при выполнении каждого задания.

Учёт начинается с первого успешного подключения observer. Позиция потока и граница
сохраняются в PostgreSQL. Модуль дополнительно сохраняет границу первой установки
в `cutoff_file`; этот файл должен переживать перезапуски и быть общим для процессов.
После восстановления observer догоняет сохранившиеся события. Данные, уже потерянные
при purge, восстановить таким способом нельзя. Изменение штатной политики комнаты
по-прежнему влияет на всю серверную историю, включая историю до начала учёта службы.

## Установка в существующий Synapse

Основной Compose разворачивает службу, PostgreSQL и RabbitMQ. Существующий Synapse
остаётся под управлением вашего текущего Compose/Ansible.

1. Подготовить проект и секреты:

   ```bash
   git clone https://github.com/heavy-mt/retentionbot.git
   cd retentionbot
   cp .env.example .env
   mkdir -p secrets
   chmod 700 secrets
   openssl rand -hex 32 > secrets/synapse_module_secret
   openssl rand -hex 32 > secrets/postgres_admin_password
   chmod 444 secrets/*
   chmod 600 .env
   ```

   Файлы читают контейнеры с разными UID. Каталог секретов на хосте доступен только владельцу;
   каждый контейнер получает только явно назначенные ему файлы.

2. В `.env` задать доступный **внутренний** URL Synapse, имя его Docker-сети и разные
   случайные hex-пароли PostgreSQL/RabbitMQ. Сеть должна существовать.

3. Собрать образ службы и образ Synapse с модулем:

   ```bash
   docker compose build
   docker build -f deploy/Dockerfile.synapse -t retention-synapse:1.161.0 .
   ```

4. В существующей установке Synapse выбрать `retention-synapse:1.161.0`.
   Добавить read-only mount файла
   `/opt/retentionbot/secrets/synapse_module_secret:/data/retention-module-secret:ro`
   (с фактическим путём проекта на хосте).

5. Добавить модуль из [deploy/synapse-module.yaml.example](deploy/synapse-module.yaml.example)
   в итоговую конфигурацию Synapse. Сохранить текущий retention; пример предназначен
   для выбора значений на стенде. Существующий список `modules` нужно дополнить.

6. Перезапустить Synapse, затем запустить службу:

   ```bash
   docker compose up -d --scale worker=4
   docker compose logs --no-log-prefix -f observer worker
   docker compose exec observer retentionbot status
   ```

Модуль устанавливается на процессы Synapse, обслуживающие его API. Для запуска через
generic worker используется тот же образ и конфигурация. Secret и уже созданный
`cutoff_file` доступны каждому такому процессу. Если workers используют read-only
volume, сначала инициализировать маркер на основном процессе, затем запускать workers.
Один observer; число внешних worker определяется по нагрузочному тесту.

На публичном reverse proxy закрыть `/_synapse/retention/v1/internal/`:
этот маршрут доступен только службе через внутреннюю сеть. Публичное управление,
если требуется, разрешается отдельно для точного маршрута
`/_synapse/retention/v1/command` с обычной аутентификацией Matrix.

## JSON-управление

Команды передаются в API или CLI. Администратор комнаты использует свой Matrix
access token. Сервер проверяет участие, актуальные права администратора
(по умолчанию уровень 100, с учётом создателей новых версий комнат) и штатные правила
отправки `m.room.retention`. Служебный ключ модуля предназначен только для внутренних
заданий и не подходит для команд пользователя.

```json
{"command":"retention","action":"set","room_id":"!room:example.org","min_lifetime":"1h","max_lifetime":"7d"}
```

```json
{"command":"retention","action":"status","room_id":"!room:example.org"}
```

Действия: `set`, `status`, `help`, `off`. Сроки — целое число миллисекунд или
строки `1h`, `7d`, `30d`, с единицами ms/s/m/h/d/w/y.
`off` доступен, когда глобальная политика не задаёт обязательный максимум.
Обычный участник может читать статус; настройку меняет администратор комнаты.

Пример CLI: токен хранится в отдельном файле, читаемом пользователем запуска.

```bash
docker run --rm --network matrix_net --user "$(id -u):$(id -g)" \
  -v "$PWD/operator-token:/operator-token:ro" retentionbot:0.2.0 command \
  --synapse-url http://matrix-synapse:8008 --token-file /operator-token \
  --json '{"command":"retention","action":"set","room_id":"!room:example.org","min_lifetime":"1h","max_lifetime":"7d"}'
```

API: `POST /_synapse/retention/v1/command`, `Authorization: Bearer <токен пользователя>`.
Ответы и записи приложения — по одному JSON-объекту на физической строке.
Переносы внутри строк экранируются. Тексты переписки, ciphertext, токены и ключи
файлов не записываются в метаданные, очередь и прикладные логи.
В чат отправляются только обычные события Matrix; текст JSON-команды в E2EE-чате
серверная служба прочитать не сможет.

## Хранилище и очередь

Основная поставка: `postgres:18.6-bookworm`, постоянный том `/var/lib/postgresql`,
роль приложения без superuser. Используется новая схема `server`.

SQLite сохраняется как вариант для одной машины: убрать `DATABASE_URL`, использовать
постоянный локальный `/data/server.db` и общий том observer/worker. Готовый основной
Compose рассчитан на PostgreSQL для заявленного потока более 100 сообщений/с.

RabbitMQ `4.3.6` запускается в этом же Compose, в отдельной внутренней сети.
Её участники — только observer, worker и сам брокер. У Synapse нет доступа к брокеру.
Опубликованных портов PostgreSQL/RabbitMQ нет. Доставка — quorum/durable, persistent,
publisher confirms и manual ack; один узел обеспечивает сохранность, а не HA.

Позиция потока сохраняется атомарно с событиями. Сроки хранятся в БД; TTL очереди
не используется. Потерянная публикация восстанавливается после пятиминутной аренды.
Native distributed lock Synapse и проверка сохранённой redaction защищают повторную
доставку, включая параллельные запросы. Успешные метаданные очищаются спустя семь дней;
незавершённые и пропущенные задания сохраняются для разбора.

## Вложения и клиентский кэш

Очистка файлов на сервере настраивается отдельной штатной политикой
`media_retention`. Она удаляет файлы и миниатюры после периода **без обращений к ним**.
Это другой срок, чем retention сообщения. Защищённые и карантинные файлы имеют
исключения. Пример настройки приведён в конфигурации модуля.

В E2EE сервер не видит ссылку на вложение внутри сообщения. Удаление файла ровно
по сроку последней ссылки потребует отдельной интеграции, передающей такие связи.
В версии 0.2 этой связи нет; привязка файла только к пользователю или времени
загрузки была бы недостаточна для безопасного удаления общих файлов.

Element X может показывать отметку об удалении. Кэш, скачанные файлы и резервные
копии устройства служба физически не стирает. Длительный офлайн до purge исходного
события может помешать доставке redaction, даже если сама redaction ещё хранится.
Универсальная гарантия очистки локального кэша в эту поставку не входит.

## Переход с 0.1 и проверки

Если старая версия была запущена: остановить её через прежний Compose, удалить
orphan-службы и отдельно вывести прежнего бота из комнат/деактивировать его аккаунт.
Новая версия сама учётную запись бота не использует и его членство не меняет.
Старые схемы `bot/gateway` не воспроизводятся; новую границу учёта создаёт версия 0.2.
Резервировать БД службы, RabbitMQ и конфигурацию/маркер Synapse согласованно.

```bash
python3.12 -m venv .venv
.venv/bin/pip install -e '.[dev]'
python3.12 -m venv .synapse-env
.synapse-env/bin/pip install matrix-synapse==1.161.0
.synapse-env/bin/pip install --no-deps -e .
.venv/bin/ruff check src tests
SYNAPSE_PYTHON="$PWD/.synapse-env/bin/python" .venv/bin/pytest -q
```

SDK с E2EE устанавливается только в dev-окружение для проверки настоящего
зашифрованного обмена между двумя тестовыми пользователями. Образы службы и модуль
его не используют. `TEST_DATABASE_URL` повторяет тесты на PostgreSQL;
`RABBITMQ_TEST_URL` включает проверку реальной очереди. CI также собирает оба
образа и запускает Compose с настоящим Synapse и ограниченной ролью PostgreSQL.
