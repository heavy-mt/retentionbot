# Проверка серверной версии 0.2

## Автоматические проверки

Тесты используют настоящий Synapse 1.161.0 и двух обычных пользователей.
Учётная запись бота в тестовых комнатах отсутствует.

| Сценарий | Проверка |
| --- | --- |
| Личный чат, версии комнат 10 и 12 | Два участника, JSON-настройка администратором, redaction в sync |
| Обычный участник | Срок изменить не может |
| Настоящий E2EE | Получатель расшифровывает сообщение, затем получает redaction; служба ключей не имеет |
| Локальный автор вышел | Событие удаления создаётся без возвращения автора в комнату |
| Права на self-redaction ограничены | Используется существующий локальный модератор |
| Дубликат/параллельные задания | Один результат удаления, состав устройств и участников сохранён |
| Изменение срока | Задание повторно проверяет текущую политику на сервере |
| История до observer | Метаданные старой истории не ставятся в очередь |
| State events | Настройки и участники комнаты не удаляются |
| Догоняющий поток | Позиция сохраняется вместе с событиями, содержимое не передаётся службе |
| До/после настоящего purge | Штатная очистка работает; потерянное событие получает missed |
| Сбой публикации и аренда | Незавершённое задание возвращается в обработку |
| PostgreSQL и SQLite | Один набор проверок на обоих движках |
| Настоящий RabbitMQ | Постоянное задание, повторная доставка после nack |
| Docker | Образы службы и Synapse, Compose, ограниченная роль БД, изолированная сеть брокера |

## Стенд заказчика

1. Сохранить конфигурацию и резервные копии. Установить модуль на проверенной версии
   Synapse, настроить доступ к внутренним API и постоянному cutoff-файлу.
2. Открыть личные чаты на Android и iOS. Убедиться, что участников ровно два и служебных
   устройств у пользователей не появилось.
3. Проверить текст, файл, изображение, голосовое сообщение, редакцию и реакцию в обычной
   и зашифрованной переписке. Назначить короткий тестовый срок с подходящим запасом.
4. Дождаться удаления при открытом чате, закрытом чате и приложении в фоне. Зафиксировать
   задержку и наличие отметки об удалении. Проверить последующий запуск без перелогина.
5. Повторить с кратким офлайном. Отдельно проверить офлайн до момента после purge:
   это сценарий с возможным пропуском redaction, а не обещанная очистка любого кэша.
6. Проверить, что сообщения до начала учёта сохраняют поведение штатного retention.
7. Проверить права администраторов, обычных участников и новые версии комнат.
8. Проверить федеративную комнату: локальный автор, чужой автор с локальным модератором,
   чужой автор без локального модератора. Последний сценарий должен иметь явный статус.
9. Перезапустить observer, worker, RabbitMQ и Synapse. Проверить догоняющий поток,
   сохранение границы учёта и отсутствие повторных redaction.
10. Проверить несколько процессов Synapse и внешний worker: единый cutoff, общий ключ,
    репликацию и параллельные задания. Обновление версии Synapse требует повторного теста.
11. Проверить физическую очистку истории на сервере. Для медиа отдельно проверить
    установленный срок без обращений, миниатюры и исключения для защищённых файлов.
    Получение redaction не означает удаления файла по тому же таймеру.
12. Подать ожидаемую длительную нагрузку более 100 сообщений/с. Измерить API задержки,
    отставание потока, возраст задач, размеры БД, CPU/диск и время доставки на телефоны.
    Успех функциональных тестов сам по себе не подтверждает эту производительность.

## Критерии

Состав личных чатов сохраняется. При исправной связи redaction приходит на действующие
клиенты без перелогина. Штатный retention включён. JSON-управление проверяет актуальные
права. Брокер изолирован. Ошибки и пропуски видны и не выдаются за успешно доставленное
удаление. Допустимые задержки на телефонах, поведение офлайна и сроки файлов фиксируются
по результатам стенда.
