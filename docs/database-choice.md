# SQLite или PostgreSQL

Решение для текущей поставки: **PostgreSQL 18.6 в Docker Compose**, с сохранением поддержки
SQLite для разработки и установки на одном хосте с умеренной нагрузкой.

Исходное требование заказчика — суммарный поток **более 100 сообщений в секунду**.
Если это постоянная нагрузка, даже 100 сообщений/с дают 8 640 000 событий/сутки и 60 480 000
за неделю. Редакции, реакции, ссылки на файлы и служебные события увеличивают количество.
Если это только редкие пики, потребность в PostgreSQL слабее.

SQLite нельзя отвергать на основании «100 записей/с»: быстрые короткие транзакции она выполняет
с большим запасом. Локальная синтетическая проверка на миллионе записей подтвердила, что скорость
отдельных вставок здесь не является ближайшим пределом. Этот замер в временной среде не переносится
на рабочие SSD, fsync, серверную нагрузку и реальные задержки Matrix API.

| Критерий | SQLite | PostgreSQL |
| --- | --- | --- |
| Один Docker-хост и мало писателей | Достаточна, проста в эксплуатации | Дополнительная служба |
| Несколько worker | Возможны на одном хосте, записи сериализуются | Общая БД с параллельными транзакциями |
| Несколько Docker-хостов | Нельзя разделять WAL через сетевой том | Доступ по сети |
| Миллионы событий ежедневно | Нужны индексы, план диска и наблюдение за блокировками | Удобнее масштабирование, резервирование и сопровождение |
| Docker | Файл и WAL в постоянном локальном `/data` | Собственный контейнер и постоянный том |

PostgreSQL выбрана под ожидаемый масштаб и параллельную обработку, а не потому что SQLite
«не умеет 100 сообщений/с». Сквозную производительность определяют также Synapse, его лимиты,
время API-запросов, E2EE и число worker. В пилоте нужно измерить задержку очереди, скорость
redaction, I/O, блокировки, размер БД и восстановление после остановки.

Планировщик уже использует индекс по комнате и сроку, не сканирует все непросроченные сообщения
на каждом тике. Healthcheck не делает полный COUNT истории. Автоматическая архивация завершённых
метаданных пока не реализована: при постоянном таком потоке это отдельный пункт перед рабочим вводом,
независимо от движка БД.

Тег `postgres:18.6-bookworm` проверен 1 октября 2026 по официальному перечню Docker-тегов.
Версия 18.4 уже не актуальная минорная версия ветки 18. Для PostgreSQL 18 том смонтирован
в `/var/lib/postgresql`; пользователь приложения не superuser, порт 5432 наружу не опубликован.
